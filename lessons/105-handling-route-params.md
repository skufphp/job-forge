## Урок 105. Обработка параметров маршрутов (Handling Route Params)

Хорошо.

Это будет довольно сложное видео, потому что нам предстоит сделать достаточно много изменений в роутере, особенно в методе `route`.
Цель — вместо перехода на `listing` с передачей `id` через query-строку (`?id=...`) сделать возможность обращаться к ресурсу так:

```
listing/ID
```

То есть просто `listing/1`, `listing/5` и т.д.

---

### 🔧 Рефакторинг роутера

Для этого нам нужно немного поработать с роутером. Да, нас ждёт ещё один рефакторинг роутера.

Открываем `router.php`.
Работать мы будем в основном в методе `route`.

---

### 🧭 Новый формат маршрутов

Теперь в файле `routes.php` мы хотим задавать маршруты не так:

```
listing
```

а вот так:

```
listing/{id}
```

Параметр `{id}` мы указываем в фигурных скобках — так же, как это делается в Laravel и большинстве фреймворков.

> В Express, например, используется формат `:id`, но мы будем придерживаться Laravel-подхода.

---

### ❌ Почему сейчас ничего не работает

Если сейчас попробовать открыть страницу деталей, она не будет работать, потому что маршрут `listing/1` не совпадает ни с одним существующим маршрутом.
Роутер не понимает, что делать с этим `1`.

Значит, мы должны научить роутер **обрабатывать параметры маршрута**.

---

### 🔄 Перенос определения HTTP-метода в роутер

Раньше в `public/index.php` мы получали HTTP-метод и передавали его в роутер.
Теперь мы это изменим: **роутер сам будет определять HTTP-метод**.

Почему?

Потому что позже, при обновлении или удалении записи, мы будем эмулировать `PUT` и `DELETE` через скрытое поле формы.
И роутер должен учитывать это.

Поэтому:

* убираем передачу метода из `index.php`
* внутри роутера получаем метод через `$_SERVER['REQUEST_METHOD']`

---

### 🧩 Разбиение URI на сегменты

Теперь нам нужно разобрать текущий URI на части (сегменты).

Например:

```
listing/1
```

должно превратиться в массив:

```
['listing', '1']
```

Для этого используем `explode('/')` и предварительно убираем лишние слэши с помощью `trim()`.

Чтобы проверить результат, делаем `inspect()` и `die()`.

Если открыть `listing/1`, мы увидим:

* индекс `0` → `listing`
* индекс `1` → `1`

---

### 📦 Разбиение маршрута из routes.php

Теперь делаем то же самое, но для маршрута из файла `routes.php`.

Например:

* `/` → пусто (главная)
* `listings` → один сегмент
* `listings/create` → два сегмента
* `listing/{id}` → сегмент с плейсхолдером `{id}`

Таким образом, мы можем сравнивать **URI** и **маршрут** сегмент за сегментом.

---

### ✅ Проверка совпадения маршрута

Создаём переменную `$match = true`.

Дальше выполняем несколько проверок:

1. **Количество сегментов URI и маршрута должно совпадать**
2. **HTTP-метод маршрута должен совпадать с текущим методом запроса**

Если всё совпало:

* создаём пустой массив `$params`
* начинаем проверку сегментов по очереди

---

### 🔍 Проверка каждого сегмента

Мы перебираем сегменты URI циклом `for`.

Для каждого сегмента:

* если сегмент маршрута **не совпадает** с сегментом URI
* и **не является параметром** (`{id}`)

→ значит маршрут **не совпал**, устанавливаем `$match = false` и выходим из цикла.

---

### 🧠 Определение параметров маршрута

Чтобы понять, является ли сегмент параметром (`{id}`), используем **регулярное выражение** с `preg_match`.

> Автор сразу говорит:
> *«Я не люблю регулярные выражения, и не очень в них хорош. Это отдельная тема, общая для многих языков»*

Регулярка просто проверяет:

> есть ли текст внутри фигурных скобок `{}`

Если это параметр:

* `matches[1]` содержит имя параметра (`id`)
* значение берём из URI (например `1`)

И добавляем в массив параметров:

```
$params['id'] = 1;
```

Если в маршруте указать `{name}`, то параметр будет:

```
$params['name'] = 1;
```

---

### 🚀 Вызов контроллера при совпадении маршрута

После цикла:

* если `$match === true`
* вызываем контроллер и метод

⚠️ **Важно:**
Теперь метод контроллера должен принимать `$params`.

---

### 🔄 Обновление контроллера Listing

Раньше ID получался из `$_GET['id']`.
Теперь ID берётся из `$params['id']`.

После этого всё снова начинает работать.

---

### 🚫 Обработка несуществующей записи

Если пользователь переходит, например, на:

```
listing/20
```

а такой записи нет — нужно показать ошибку.

После запроса к БД добавляем проверку:

```php
if (!$listing) {
    ErrorController::notFound('Listing not found');
    return;
}
```

Теперь отображается понятное сообщение:
**«Listing not found»**

---

### 🔙 Кнопка «назад»

В представлении ошибки добавляем ссылку:

```
Go back to listings
```

которая ведёт на `/listings`.

---

### 🧹 Финальные правки

Исправляем ссылки:

* в `home.view.php`
* в `listings/index.view.php`

Вместо:

```
listing?id=1
```

используем:

```
listing/1
```

Теперь всё работает:

* и со страницы списка
* и с главной страницы

## 🎯 Главная цель урока

**Научить твой роутер понимать URL с параметрами**, такими как:

```
/listing/5
/listing/42
```

и превращать их в **осмысленные данные**, которые можно передать в контроллер:

```php
$params['id'] = 5;
```

---

## 🧠 Что ты ДОЛЖЕН понять концептуально

### 1️⃣ URL — это не строка, а структура

Раньше ты думал о URL примерно так:

```
"listing?id=5"
```

Теперь ты должен думать так:

```
["listing", "5"]
```

👉 **URL нужно разбирать на сегменты**, а не сравнивать целиком строкой.

Это ключевая смена мышления.

---

### 2️⃣ Маршрут — это шаблон, а не конкретный путь

Маршрут:

```
listing/{id}
```

❌ **не значит** «один конкретный URL»
✅ **значит** «любой URL, который подходит под этот шаблон»

Примеры:

* `listing/1` ✅
* `listing/25` ✅
* `listing/abc` ✅ (пока да, валидации ещё нет)

---

### 3️⃣ Роутер делает сложную работу, контроллер — простую

Очень важно запомнить это разделение ответственности:

#### 🧭 Роутер:

* разбирает URL
* сравнивает его с маршрутами
* вытаскивает параметры (`id`, `slug`, и т.д.)
* **передаёт готовые данные в контроллер**

#### 🧱 Контроллер:

* **не парсит URL**
* **не читает `$_GET`**
* просто получает:

```php
$params['id']
```

💡 Это и есть MVC-мышление.

---

### 4️⃣ Почему `$_GET` — плохо для архитектуры

Раньше:

```php
$_GET['id']
```

Проблемы:

* контроллер зависит от глобального состояния
* сложно тестировать
* сложно менять формат URL
* не масштабируется

Теперь:

```php
function show(array $params)
```

Плюсы:

* контроллер **чистый**
* его можно вызывать из тестов
* формат URL можно менять, не ломая бизнес-логику

👉 **Это огромный шаг к фреймворковому мышлению.**

---

### 5️⃣ Почему это выглядит сложно — и это нормально

Ты должен запомнить важную мысль автора:

> «Это, пожалуй, самая сложная часть курса»

И это правда, потому что:

* тут **алгоритмическое мышление**
* тут **инфраструктура**
* тут **не CRUD и не SQL**

💡 **Но**: это пишется **один раз**, а используется **везде**.

## 🔑 5 вещей, которые нужно запомнить НАВСЕГДА

Запомни этот чек-лист:

### ✅ 1. URL → сегменты

```text
/listing/5 → ["listing", "5"]
```

---

### ✅ 2. Маршрут → шаблон

```text
listing/{id} → любой listing/что-угодно
```

---

### ✅ 3. Параметры маршрута ≠ query string

❌ `?id=5`
✅ `/listing/5`

---

### ✅ 4. Роутер извлекает параметры

```php
$params['id'] = 5;
```

---

### ✅ 5. Контроллер НЕ знает, откуда пришёл ID

Контроллеру **плевать**:

* был ли это URL
* был ли это API
* был ли это тест

Он просто работает с данными.

## 🧭 Как это связано с Laravel (важно!)

Ты фактически **реализовал руками** вот это:

```php
Route::get('/listing/{id}', [ListingController::class, 'show']);
```

и в контроллере:

```php
public function show($id)
```

👉 После этого урока Laravel перестаёт быть «магией».
Ты уже знаешь, **что там происходит под капотом**.
